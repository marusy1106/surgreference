# SurgReference — проектирование MVP

Образовательная мобильная платформа для студентов-медиков, ординаторов и молодых врачей: справочники (МКБ-10, клинические рекомендации), уроки, тесты с разбором, учебные клинические кейсы, прогресс, XP/уровни/достижения, добровольные рейтинги студентов и вузов.

> Приложение — **учебное**. Оно не ставит диагнозы, не выдаёт рекомендаций по лечению реальных пациентов и не обрабатывает данные пациентов. Все клинические кейсы — синтетические.

## Ключевые решения одной строкой

- **Архитектура:** модульный монолит Django 5 + DRF, PostgreSQL 16, Redis, Celery, S3-совместимое хранилище; всё в Docker; хостинг и бэкапы — в дата-центрах РФ.
- **Мобильное приложение:** один Flutter-код для iOS и Android (App Store + RuStore), Riverpod + go_router + dio, клиент API генерируется из OpenAPI.
- **API:** REST, версионирование в пути `/api/v1/`, OpenAPI-схема — единый контракт.
- **Авторизация:** email + пароль (Argon2id), подтверждение 6-значным кодом, короткий access JWT + ротируемый refresh-токен, привязанный к сессии устройства; MFA (TOTP) обязательна для админки.
- **Персональные данные:** минимум — email, никнейм, (опционально) имя, образовательный профиль. Нет телефона, даты рождения, фото, данных о здоровье.
- **Контент:** каждая единица контента версионируется и проходит статусы `черновик → на проверке → одобрено → опубликовано → в архиве`; публикация невозможна без медицинского рецензента.
- **Монетизация:** модель тарифов, прав и подписок есть в БД с первого дня, но на этапе 1 глобальный флаг `monetization_enabled = false` открывает всё всем. Платёжные SDK не подключаются до решения после 100 пользователей.
- **Аналитика:** собственная, на своём сервере (без отправки ПД сторонним SaaS); события псевдонимизированы.

## Структура будущего репозитория

```
surgreference/
├── backend/        # Django-проект (config/ + apps/)
├── mobile/         # Flutter-приложение
├── infra/          # docker-compose, nginx, скрипты бэкапа, CI
└── docs/           # эта документация
```

Папка временно лежит внутри репозитория «Точка решения»; перед стартом разработки её стоит вынести в отдельный репозиторий (это другой продукт с другим жизненным циклом).
