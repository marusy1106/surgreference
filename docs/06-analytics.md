# 6. Аналитика первых 100 пользователей

## 6.1. Принципы

- Своя система: события идут на наш backend в РФ, сторонние аналитические SaaS не используются.
- Псевдонимизация: события связаны с внутренним UUID и `install_id`, никогда — с email/именем. Аналитик видит только агрегаты; доступ к строкам событий — только у суперадмина.
- Минимизация: белый список событий и их свойств на сервере; неизвестные ключи отбрасываются; свободный текст в событиях запрещён.
- Отказ: в настройках «Не отправлять аналитику использования» — клиент перестаёт слать необязательные события (серверные факты вроде завершения теста всё равно сохраняются как часть учебного процесса).
- Хранение: сырые события — 13 месяцев, затем удаляются; агрегаты `daily_metrics` — бессрочно (не содержат ПД).

## 6.2. События

Большая часть метрик считается из **серверных** таблиц (пользователи, попытки, XP) — это надёжнее клиентских событий. Клиент присылает только то, что сервер не видит:

| Событие | Свойства |
|---------|----------|
| `app_open` | `cold_start` |
| `session_start` / `session_heartbeat` (раз в 60 с при активном приложении) / `session_end` | — |
| `screen_view` | `screen` (из перечня) |
| `onboarding_step` | `step`, `skipped` |
| `lesson_open` / `lesson_scroll_end` | `lesson_id`, `revision` |
| `search` | `results_count` (без текста запроса) |
| `review_open` | `attempt_id` |
| `leaderboard_view` | `board`, `period` |
| `theme_changed` | `theme` |

Серверные доменные события (`user_registered`, `email_verified`, `quiz_attempt_finished`, `case_attempt_finished`, `lesson_completed`, `achievement_earned`, `account_deleted`) пишутся в ту же таблицу backend'ом.

## 6.3. Определения метрик

| Метрика | Определение |
|---------|-------------|
| Зарегистрированные | `users` без `deleted_at`, кроме `is_staff` и тестовых аккаунтов |
| Подтверждённые | то же + `email_verified_at IS NOT NULL` — **счётчик пути к 100** |
| Активный пользователь за день | есть строка в `daily_user_activity` с ≥ 1 учебным действием или сессией ≥ 30 с |
| DAU / MAU | число активных за день / за скользящие 30 дней; показываем и DAU/MAU (stickiness) |
| Retention D1 / D7 / D30 | доля когорты подтверждённых за день *X*, активных в день *X+1* / *X+7* / *X+30* (классический, не «rolling»); при когортах < 20 человек показываем с пометкой «мало данных» |
| Активация | доля подтверждённых, завершивших ≥ 1 тест в первые 24 часа |
| Пройденные тесты | `quiz_attempts` со статусом `finished` за период; отдельно — среднее на активного |
| Популярные дисциплины | число уникальных пользователей и завершённых попыток/уроков по дисциплинам за период |
| Длительность учебной сессии | `app_sessions.duration_sec` (по heartbeat, разрыв > 5 мин закрывает сессию); показываем среднее **и медиану** |
| Пользователи по вузам | подтверждённые по `education_profiles.university_id`; вузы с < 3 пользователями объединяются в «Другие» для внешних отчётов |
| Обратная связь и ошибки | число `feedback` по типам и статусам, средняя оценка, ошибки в контенте по дисциплинам, crash-free sessions из Sentry |

## 6.4. Панель в админке

Отдельная страница Django Admin «Аналитика MVP» (`/admin/analytics/dashboard/`), роль `analyst` и выше:

1. **Путь к 100** — прогресс-бар «подтверждено N из 100», регистрации vs подтверждения по дням, воронка: установка → регистрация → подтверждение → профиль → первый тест.
2. **Активность** — DAU, WAU, MAU, stickiness за 90 дней.
3. **Удержание** — когортная таблица D1/D7/D30 по неделям регистрации.
4. **Обучение** — тесты/кейсы/уроки по дням, средний результат, популярные дисциплины, распределение длительности сессий.
5. **Вузы** — топ вузов по числу пользователей, распределение по статусам и курсам.
6. **Качество** — открытые сообщения об ошибках в контенте, отзывы, средняя оценка, crash-free.

Реализация: агрегаты из `daily_metrics` (ночной Celery-расчёт за прошлые сутки + «сегодня» на лету с кешем 5 минут), графики — Chart.js в шаблоне админки, выгрузка CSV только агрегатов. Каждое открытие панели и выгрузка пишутся в журнал.

## 6.5. Порог 100 пользователей

Ежечасная задача считает подтверждённых. При достижении 100:

- записывается `system_milestones('confirmed_users_100')`;
- первым 100 присваиваются `founder_number` 1–100 (порядок — по `email_verified_at`) и достижение «Основатель»;
- суперадминам уходит письмо, в админке появляется баннер «Достигнут порог 100 — подготовьте решение о монетизации» со сводкой метрик.

Платный доступ при этом **не включается** — см. [07-monetization.md](07-monetization.md).
